# Developer Path — Building the Thesis Codebase Step by Step

This is a working guide for developing the thesis project **one feature at a time**. You stay in control, you always know what each part of the code does, and a broken feature never blocks the rest of the project.

---

## 0. Guiding Principles

1. **Small steps, always working.** The `main` branch should always run. New work happens on a separate branch.
2. **One feature = one branch = one folder/module.** If a feature fails, you park its branch and start another. Nothing else breaks.
3. **Write it down before you code it.** Every feature gets a short entry in `docs/FEATURES.md` that says what it does, its inputs and outputs, and its status.
4. **Reproducibility over cleverness.** Anyone, including future you, should be able to clone the repo and reproduce a result with one command.
5. **Configuration, not hardcoding.** Model names, paths, and hyperparameters go in config files, not inside the code.
6. **You review every change.** Whether code comes from you, a tutorial, or an AI assistant, read the diff and understand it before you commit.

---

## 1. Phase 1 — Plan Before Code (≈1–2 days)

Create `docs/` and write these short documents:

| File | Content |
|------|---------|
| `docs/PROJECT_OVERVIEW.md` | Thesis goal, research questions, what "done" looks like |
| `docs/ARCHITECTURE.md` | Block diagram: data → preprocessing → model (e.g. `qwen3-vl:2b` via Ollama) → evaluation → results |
| `docs/FEATURES.md` | Feature backlog and status tracker (template in §6) |
| `docs/DECISIONS.md` | Log of important decisions and why (e.g. "Chose Ollama over HF transformers because…") |

**Break the thesis into features.** A feature is something small enough to finish in 1–5 days and test on its own. Example backlog:

- F1: Load and validate the dataset
- F2: Wrapper for calling the local model (Ollama API)
- F3: Prompt templates
- F4: Run inference on a batch and save outputs
- F5: Evaluation metrics
- F6: Experiment runner (config → run → results folder)
- F7: Plots and tables for the thesis

## 2. Phase 2 — Set Up the Repository (≈½ day)

### 2.1 Local repo
```bash
cd ~/thesis
git init
git branch -M main
```

### 2.2 Recommended folder structure
```
thesis/
├── README.md               # What the project is, how to install and run it
├── developer_parth.md      # This guide
├── .gitignore
├── environment.yml         # Conda environment (or requirements.txt)
├── configs/                # YAML configs: model names, paths, hyperparameters
│   └── default.yaml
├── data/                   # NOT committed (see .gitignore)
│   ├── raw/                # Original data, never modified
│   └── processed/          # Generated by code
├── src/thesis/             # Your Python package: one module per feature
│   ├── __init__.py
│   ├── data/               # F1: loading and preprocessing
│   ├── models/             # F2: model wrappers (Ollama client etc.)
│   ├── prompts/            # F3: prompt templates
│   ├── inference/          # F4: running predictions
│   ├── evaluation/         # F5: metrics
│   └── utils/              # Logging, config loading, seeding
├── scripts/                # Entry points: run_inference.py, evaluate.py
├── notebooks/              # Exploration ONLY; move final logic into src/
├── tests/                  # One test file per module
├── experiments/            # Results per run (NOT committed, or only summaries)
└── docs/                   # Planning and documentation
```

**Why this layout:** each feature lives in its own folder, so you always know which part does what. Notebooks are for experimenting, and code that works graduates into `src/`.

### 2.3 `.gitignore` essentials
```
# Python
__pycache__/
*.pyc
.ipynb_checkpoints/
.venv/

# Data, models, results (too large / private)
data/
experiments/
*.gguf
*.safetensors
*.bin

# Secrets
.env
```
Never commit model weights (your `~/hf-cache` lives outside the repo, which is good), datasets, or API keys.

### 2.4 Environment
You have conda available. Create a dedicated environment:
```bash
conda create -n thesis python=3.11 -y
conda activate thesis
pip install pyyaml requests pytest ruff
conda env export --from-history > environment.yml   # commit this file
```
Each time you add a library, update `environment.yml` and commit it.

### 2.5 GitHub
1. Create an **empty** repository on GitHub (no README; you already have one locally).
2. Connect it and push:
```bash
git add .
git commit -m "chore: initial project structure"
git remote add origin git@github.com:<your-username>/<repo-name>.git
git push -u origin main
```
3. Keep the repo **private** until your supervisor or university says it's fine to make it public.

## 3. Phase 3 — The Feature Workflow (repeat for every feature)

This loop is how you stay in control and switch features when one gets stuck.

```
 ┌──────────────────────────────────────────────────────────────┐
 │ 1. Pick a feature from docs/FEATURES.md → mark "In progress" │
 │ 2. git checkout -b feature/F2-ollama-client                  │
 │ 3. Write a small spec (inputs, outputs, how to test)         │
 │ 4. Implement in src/thesis/<module>/                         │
 │ 5. Write tests in tests/                                     │
 │ 6. Run it: pytest + a small script                           │
 │ 7. Commit small, meaningful steps                            │
 │ 8. Works?  → merge into main, mark "Done"                    │
 │    Stuck?  → commit WIP, push branch, mark "Blocked" + note, │
 │              git checkout main, start the next feature       │
 └──────────────────────────────────────────────────────────────┘
```

### Commands
```bash
# start a feature
git checkout main
git pull
git checkout -b feature/F2-ollama-client

# save progress
git add src/thesis/models/ollama_client.py tests/test_ollama_client.py
git commit -m "feat(models): add Ollama client with generate()"

# feature is done: merge it
git checkout main
git merge --no-ff feature/F2-ollama-client
git push

# feature is stuck: park it
git add .
git commit -m "wip(models): image input not working yet, see FEATURES.md"
git push -u origin feature/F2-ollama-client
git checkout main
git checkout -b feature/F5-metrics
```

On GitHub you can also open a **Pull Request** for each feature branch, even when working alone. It gives you a clean page that shows exactly what changed, which is useful when you write the thesis later.

### Commit message convention
```
<type>(<module>): <short description>

types: feat | fix | refactor | test | docs | chore | exp
```
Examples:
- `feat(data): load images and captions from CSV`
- `fix(inference): handle empty model response`
- `exp: run baseline prompt on 100 samples`

## 4. Phase 4 — Coding Practices

### 4.1 Keep modules independent
Each module has a clear input and output. Example:
```python
# src/thesis/models/ollama_client.py
class OllamaClient:
    """Talks to a local Ollama server. Knows nothing about datasets or metrics."""
    def generate(self, prompt: str, image_path: str | None = None) -> str: ...
```
If the Ollama client breaks, data loading and metrics still work and can still be tested.

### 4.2 Config files instead of hardcoded values
```yaml
# configs/default.yaml
model:
  name: qwen3-vl:2b
  host: http://localhost:11434
  temperature: 0.0
data:
  raw_dir: data/raw
seed: 42
```

### 4.3 Logging instead of `print`
Use Python's `logging` module so you can see what each part is doing and turn detail up or down.

### 4.4 Docstrings and type hints
Every function says what it does, what it takes, and what it returns. This is how you "know which part is doing what."

### 4.5 Code quality tools
```bash
ruff check src tests     # find errors and style issues
ruff format src tests    # auto-format
pytest                   # run tests
```
Run these before every commit.

### 4.6 Tests
- Test each module separately (`tests/test_data.py`, `tests/test_metrics.py`, …).
- For the model, test with a tiny input and check the output type and format, not exact text.
- A feature counts as **done** only when its tests pass.

## 5. Phase 5 — Experiments and Reproducibility (critical for a thesis)

1. **Every run gets its own folder:** `experiments/2026-11-20_baseline/` containing the config used, outputs, metrics, and logs.
2. **Record the git commit hash** in each run folder (`git rev-parse HEAD`), so every result traces back to exact code.
3. **Fix random seeds** (Python, NumPy, model temperature = 0 where possible).
4. **Record model versions:** `ollama list` output (model ID `0635d9d857d4` for `qwen3-vl:2b`).
5. Keep an **experiment log** in `docs/EXPERIMENTS.md`: date, what changed, result, conclusion.
6. Optional later: MLflow or Weights & Biases for experiment tracking, and DVC for data versioning.

```markdown
- **Output:** model response (str)

- **Test:** tests/test_ollama_client.py
- **Status / notes:** …
```

## 7. Working With an AI Assistant While Staying in Control

- Ask for **one feature or one function at a time**, not "write the whole project."
- Ask for an explanation of the code, and read the diff (`git diff`) before committing.
- Commit AI-assisted code only after you understand it and its tests pass.
- Keep the design decisions (architecture, what to measure, which experiments) yours, and log them in `docs/DECISIONS.md`. Your examiners will ask about them.

## 8. Step-by-Step Checklist

**Setup**
- [ ] Write `docs/PROJECT_OVERVIEW.md` (thesis goal, research questions)
- [ ] Write the feature backlog in `docs/FEATURES.md`
- [ ] `git init`, create the folder structure, `.gitignore`, `README.md`
- [ ] Create the `thesis` conda environment and export `environment.yml`
- [ ] Create a private GitHub repo and push the initial commit

**First features (suggested order)**
- [ ] F0: Utilities: config loading, logging, seeding
- [ ] F1: Data loading
- [ ] F2: Model client (Ollama `qwen3-vl:2b`)
- [ ] F3: Prompts
- [ ] F4: Batch inference
- [ ] F5: Evaluation
- [ ] F6: Experiment runner
- [ ] F7: Figures and tables for the thesis

**Continuously**
- [ ] One branch per feature; `main` always works
- [ ] Small commits with clear messages
- [ ] Update `FEATURES.md` status whenever you start, finish, or park a feature
- [ ] Push to GitHub at the end of every working session
- [ ] Log every experiment in `docs/EXPERIMENTS.md`
- [ ] Meet your supervisor with the `FEATURES.md` and `EXPERIMENTS.md` as your progress report

## 9. Quick Reference

| Task | Command |
|------|---------|
| Start Ollama server | `OLLAMA_MODELS=~/hf-cache ~/.local/bin/ollama serve &` |
| New feature | `git checkout main && git checkout -b feature/FX-name` |
| Save work | `git add <files> && git commit -m "feat(module): ..."` |
| Finish feature | `git checkout main && git merge --no-ff feature/FX-name && git push` |
| Park feature | commit WIP → `git push -u origin feature/FX-name` → `git checkout main` |
| Check quality | `ruff check src tests && pytest` |
| See what changed | `git status`, `git diff`, `git log --oneline --graph` |
